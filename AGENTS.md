# Engineering standards

These apply across all projects unless a project's own `AGENTS.md` (or `CLAUDE.md`) overrides them. Each rule is stated once; agents and project files point here rather than restating it. A rule that lint or a hook can enforce is enforced there and not restated here: add the mechanism, delete the sentence.

## Default stack

- **Web apps:** Next.js + React, TypeScript.
- **Static/marketing sites** (landing pages, docs, blogs — no real client state or auth): Astro 5 + Tailwind CSS, minimal JS, a UI-framework island only for the specific component that needs interactivity.
- **Mobile:** Flutter, Dart, when one codebase for both platforms is the goal. Native when the product targets one platform or needs its full API surface: Kotlin + Jetpack Compose on Android, Swift + SwiftUI on iOS. React Native on Expo when a React team shares code and contracts with the web app.
- **BFF:** Fastify + TypeScript — a thin per-client layer that shapes/aggregates responses and translates auth/session. No business logic, no database beyond a thin cache.
- **APIs / microservices:** Fastify + TypeScript — each owns one bounded context, its logic, and its own database. Never reach into another service's database.
- **Database:** MongoDB, one logical database per service.
- **Queues & background jobs:** BullMQ + Redis.
- **Edge & WAF:** Cloudflare in front of every public app and API.

Match what an existing project already uses instead of forcing this stack on it.

- **Next.js or Astro?** Real client state, auth, a data-heavy UI, or a product that will keep growing → Next.js. Fundamentally static or content-driven → Astro.
- **BFF or direct calls?** Add a BFF when a client needs shaping/aggregation across more than one service, or a different auth/session model. A single client talking to a single service doesn't need one yet.
- **Flutter, native or React Native?** Flutter by default for a product that ships on both platforms from one team. Native (Kotlin/Compose, Swift/SwiftUI) when the app is one platform only, leans on platform APIs (widgets, background work, hardware, platform-specific UI) or must feel fully native. React Native (Expo) when the team is a React team and the app shares a backend contract, types and conventions with the Next.js app. Never two of them in one product without an ADR.

**Stack architecture lives in a skill per stack**, loaded on demand and shared by whoever writes, plans or reviews code in it: `flutter-architecture`, `android-architecture` (Kotlin, Compose), `ios-architecture` (Swift, SwiftUI), `react-native-architecture` (Expo), `nextjs-architecture` (Next.js and Astro), `fastify-architecture` (APIs, BFFs, BullMQ, MongoDB). Each holds the layout, the dependency rule as a table, a "where does X go" guide, the anti-patterns seen in reviews with the correct form, and the checklist a review brief copies. **Load the skill before writing or reviewing a line in that stack**, in the main session as much as in an agent. Agent files hold only the role, its boundaries, a few non-negotiables and the done criteria. Docker, Compose, CI and Cloudflare conventions stay in `devops-engineer.md`. Why: an architecture stated as principles in one agent's file is seen by one agent and followed loosely; a concrete layout and checklist loaded by everyone, backed by a test that fails on a forbidden import, is followed.

## Design

- **Mobile-first for apps**: build from the smallest viewport up with `min-width` breakpoints, unless the user sets a different priority for a project (e.g. a desktop-only internal tool).
- **Desktop-led for marketing pages** (landing pages, product sites): design 1280 first as a layout that sells, not one phone column stretched wide, then design 390 as its own adaptation rather than leaving it to whatever wraps. Why: a landing page's job is persuasion, and a good desktop layout is where that effort pays most.
- Either way it's verified, not assumed — a UI change isn't done until it has been looked at at ~390px as well as desktop (a phone and a tablet for a native Android, iOS or React Native app; Flutter, whose e2e tier runs on its web target, keeps 390 and desktop).
- **Airbnb is the UX reference** for structure and behaviour, not only visuals: account settings hold administrative things only; anything describing the user or what the product makes for them gets its own destination; hubs link to focused pages; summary rows show the value with an explicit `Edit`; one primary action per screen; calm neutral states; little copy. A project's own docs can override this. The full version lives in the `designer` agent.
- **Placement before polish.** Where a feature lives is a design decision in its own right, made from the user's mental model rather than from which existing screen is convenient. If a screen needs copy to explain what doesn't belong on it, the structure is wrong.
- **Rule-driven states get drawn, not only written.** When a design rule makes a screen behave in a way the user wouldn't predict (mixed languages, a hidden element, a fallback value, a state that only appears after another setting changes), that state gets its own artboard in the project's design canvas (or, without one, a mockup on the issue) for review before it's built. Why: a rule described only in prose gets approved without anyone seeing what it produces.
- **Tokens first, components second.** Each web project defines its tokens once (Tailwind v4 `@theme`: colors, type scale, spacing, radii) and everything reads them through utility classes — no raw hex/px in components. Tokens are what transfers across surfaces (Next.js, Astro, an exported Flutter theme); React components transfer only between web apps.
- **Shared primitives live in `src/shared/ui/`** (`Button`, `Field`, `FormErrorMessage`, brand mark…) with their own `feature_readme.md`. Feature code composes them and never hand-rolls a variant's class string. The same long `className` appearing in two files means a primitive is missing — extract it first; hand-rolled copies drift (one button's hover no longer matching its siblings').
- Primitives and tokens are `designer`-owned decisions. Lift them into a cross-repo package only once a second web surface actually consumes them; the mobile apps (Flutter, Android, iOS) get the tokens, never the React package; a React Native app may share the token values, never the DOM components.

## Code principles

- Small functions with one responsibility; extract when a function does two things, not before. Names say what something is or does.
- Guard clauses over nested conditionals. No magic numbers or strings. No dead code, commented-out blocks, or abstractions for hypothetical needs.
- **Comments explain why, briefly** — a few lines at most. History (which ticket, which ADR, what it replaced) belongs in the PR or ADR, not in the code, where it goes stale. Prefer renaming or restructuring over a comment that explains what code does. Don't imitate essay-length comments just because surrounding code has them.
- SOLID, in practice: one reason to change per module; extend by adding code rather than special-casing working code; implementations substitutable without the caller knowing which it got; narrow interfaces; depend on abstractions (that's why services depend on repository interfaces, not the Mongo driver).
- Clean Architecture: inner layers (domain, use-cases) never import outer ones (frameworks, DB drivers, HTTP, UI). Business logic is framework-agnostic and unit-testable with nothing running. I/O sits behind ports owned by the inner layer; adapters implement them. Controllers, routes and widgets are thin.

### Structure rules (checkable)

Principles drift; these are concrete enough to fail a review or a lint run. Each stack's architecture skill shows the layout that satisfies them.

- **Feature code in `shared/` needs two importing features.** Feature logic moves to `shared/` (or `core/`) only when a second feature imports it; until then it lives in the feature that uses it, even if it "looks reusable". Exempt: app infrastructure imported by the app's composition root (config, logger, transport, error envelope, session codec, database and queue connection plumbing) and the design system (`shared/ui`, tokens), which follow their own rules above.
- **A feature owns the calls it makes.** Each call to another service, a database or a third-party API goes through a narrow port owned by the feature: an interface plus an adapter on the backend, a module of narrow functions in `lib/` on the frontend. The port declares only the operations that feature uses, and the request/response types for them live beside it. On the backend, `shared/` holds the infrastructure the bullet above exempts and, past its two-importers rule, types, pure rules and reference data; never a repository or a use-case, which belong to a feature. Each other stack's architecture skill says what its `shared/` or `core/` holds. A module receives the narrowest interface it uses: a Fastify plugin's options name the feature's port type, never a client with every operation in the system.
- **Dependency direction.** A feature imports another feature only through its public surface: the exports its `feature_readme.md` lists under "exposed interface" (or its `index.ts`, where the repo uses one). `shared/` never imports a feature; inner layers never import outer ones.
- **Size, for new and rewritten code.** About 300 lines per file and 40 per function, counting no blanks or comments. Exempt: tests, pure data/type/schema files (i18n dictionaries, generated types), a framework's plugin wrapper (a Fastify plugin function whose body only registers routes), and components, which get ~200 lines in the UI agents' rules.
- **File names follow the stack, not the symbol inside.** TypeScript (Next.js, Astro, Fastify): kebab-case files and folders (`login-form.tsx`, `http-core-api-auth.ts`, `build-account-deletion.ts`), with dotted role suffixes (`*.test.ts`, `*.redis.test.ts`, `*.spec.ts`); the class, component or function inside keeps its PascalCase or camelCase name. Dart: snake_case (`tweet_feed_cubit.dart`), as Effective Dart requires. Kotlin and Swift: PascalCase after the one top-level type the file holds (`FeedViewModel.kt`, `FeedViewModel.swift`), as their style guides require. React Native follows the TypeScript rule. Framework-reserved names stay as the framework wants them (`page.tsx`, `layout.tsx`, `route.ts`, `[slug]/`, `(app)/`, Expo Router's `_layout.tsx` and `+not-found.tsx`), and so does `feature_readme.md`. Why: the file system on Windows and macOS ignores case, so a file named after its class breaks on a case-only rename and lets an import with the wrong case pass locally and fail in CI; Kotlin and Swift name files after the type because their style guides require it, and the lint named below catches a name that disagrees with the type; and one convention per repo keeps folders and files from disagreeing. Enforced by lint: `unicorn/filename-case` (`kebabCase`) in ESLint, `file_names` in Flutter's lints, ktlint's `filename` rule, SwiftLint's `file_name`. A repo still on another convention keeps it consistently until its own rename PR, which moves every file at once and adds the lint rule, rather than mixing both conventions file by file.
- **Don't extend a violation.** Match the surrounding code's style, not its structural mistakes; "the file already did it this way" is never the reason. When the code you touch already breaks a rule, this takes precedence over Size: fix it in the same PR only if the fix is small (under ~50 changed lines, no behaviour or contract change, covered by existing tests). Otherwise build your change the right way beside it, link the existing refactor issue or open one, and list it under Deviations. Never start an unasked refactor of a file you only needed to add to.
- **Contracts aren't refactors.** Response and error-envelope shapes a client depends on are contracts: changing one is a tracked change with its own issue and the client updated together, never a side effect of tidying.
- **Enforced by lint or a test once a repo opts in.** A repo adopts boundary and size rules (`eslint-plugin-boundaries` or `dependency-cruiser`, `max-lines`, `max-lines-per-function`; in Flutter an architecture test that scans `lib/` imports against the dependency table; on Android the Gradle module graph plus a Konsist test and detekt's size rules; on iOS the package graph plus an import-scanning test and SwiftLint's length rules) through its own ticket, with a baseline: today's offenders listed as per-file overrides that may only shrink. Where a repo has them, run them before reporting work done. Never add a disable comment to get past them.

## Feature folders

Organize by feature, not technical type, in every stack — `features/checkout/` holding its own components/hooks, routes/services/repositories, or presentation/domain/data — with cross-feature code in `shared/` or `core/`. The internal layering is stack-specific (see the stack's architecture skill).

**A feature's shape follows its size**, for new and rewritten features. A layer folder appears with the second file of its kind, never before, except the folders the stack's skill names as present from the start. When a layer folder passes about 15 non-test source files, the feature splits by sub-feature, not by layer, each with the layers it needs and its own `feature_readme.md`, the parent holding only its readme and the code every sub-feature shares. The features folder is never grouped into module folders: a parent feature has its own readme and shared code; a folder holding only child features is a module folder. An existing feature changes shape in its own issue, never as a side effect of adding a file. Each stack's skill names the split example and, where the stack has flat files, the lint element type each stands for. Why: the full skeleton on a five-file feature hides the code behind its folders, one folder of forty files hides which pieces belong together, and a module layer over the features folder adds a path segment to every import for a grouping that will be wrong once.

**Every feature folder has a `feature_readme.md`**: purpose, exposed interface (routes, use-cases, exported components/hooks), and key data flow. Create it with the feature; update it when it would otherwise mislead, not on every commit.

## Testing

- Unit-test business logic with no framework, database or network. Integration-test repositories against a real/test MongoDB, routes through Fastify's `inject`, and BullMQ processors against a real/test Redis (including the retry path).
- Frontend e2e: Playwright (web) or `integration_test` (Flutter) for critical flows, running **at least a desktop and a mobile (~390px) project or window** — a desktop-only suite has never exercised a mobile-first layout. Layout assertions belong in the mobile project too. Flutter e2e runs against the app's in-memory backend; the mechanics are in the `flutter-architecture` skill. Native Android, native iOS and React Native apps have the same tier, at least a phone and a tablet, each against the app's in-memory backend: instrumented Compose flows on a managed device (Android), XCUITest (iOS), Maestro on both platforms (React Native); screenshot tests per screen state are how those stacks meet the two-viewport rule. The mechanics are in each stack's architecture skill.
- **A test that never opens a page is a unit test**, in vitest, never a Playwright spec: a spec that only imports a `lib/` function and asserts on its return value runs in a browser harness, once per project, for nothing, and that is where the slow suite comes from. Keep a `test:e2e:smoke` script (sign-in, home, the header at 390, route guards), or `integration_test/smoke_test.dart` in Flutter, for the fast CI tier.
- **UI changes ship with screenshots at both viewports** (phone and tablet, light and dark, for a native Android, iOS or React Native app), for every relevant state (signed in/out, error, pending, empty), linked in the PR. Whoever implements produces them, and not having run the app is a blocker to resolve, not a caveat.
- Don't mock what you're testing, or so much that the test proves nothing.
- **A test double for a boundary is checked against the real boundary.** A fake server or a fixture of another service's response is validated in CI against that service's published schema (and its CORS headers, where a browser is involved). A fake that only agrees with itself stays green while the real thing is broken; that is how a response-shape change shipped three times with every suite passing.
- **UI is verified in every locale the project ships**, not only the default, and a change that crosses a service boundary gets a signed-in pass on the real local stack, reading a record that has data in it. Health endpoints and fakes prove nothing about the boundary.
- **Never accept a self-reported "tests pass".** Re-run the same commands yourself before calling work done, whether or not the agent's shell worked.
- **A running server proves nothing about which code it runs.** After a merge or a dependency change, restart the local stack before demoing or verifying against it: a stale process still answers `200`, so a health check isn't evidence.

## Agents

The roster lives in `agents/` of the agent-config repo and is installed into each tool's own agents folder (`docs/architecture.md`). These standards authorize dispatching them proactively when a task matches their domain.

- **product-strategist** — turns a new product idea into scope, users, priorities and a phased roadmap. No tech opinions.
- **architect-engineer** — boundaries and topology when a change spans layers/features, introduces a pattern, or touches shared code (BFF vs direct, new service vs extend, queue vs sync).
- **designer** — which screen a feature belongs on, new components, new UX patterns, design systems; Airbnb as the UX reference.
- **backend-engineer** — Fastify implementation.
- **frontend-engineer** (Next.js, Astro, Flutter), **android-engineer** (Kotlin, Jetpack Compose), **ios-engineer** (Swift, SwiftUI), **react-native-engineer** (Expo) — implementation of the client, each on its `*-architecture` skill. Together they are *the client's engineer*: where another agent or rule says that, it means whichever of the four owns the stack at hand.
- **qa-engineer** — test strategy and verifying a change works.
- **security-engineer** — security review and threat modelling (auth, payments, external input, data exposure, edge config).
- **code-reviewer** — correctness, security and architecture review of a diff at a stated level; the review pass on tools without a built-in one. Where the tool has a built-in review pass (Claude Code's `/code-review`), use that instead.
- **technical-writer** — READMEs, API docs, ADRs, changelogs.
- **devops-engineer** — Docker/Compose, CI/CD, Cloudflare; implements topology, doesn't decide it.

Skills to reach for directly: `flutter-architecture`, `android-architecture`, `ios-architecture`, `react-native-architecture`, `nextjs-architecture`, `fastify-architecture` (before any code in that stack), `clean-code`, `security-threat-model`, `frontend-design`, `web-design-guidelines`, `open-pr`, `resolve-pr-comments`, `conventional-commit`, `archify`, `retro`, `security-audit`.

**Briefing an agent.** Agents see only your prompt and their own file. Carry the context explicitly: links to the issue and docs, the literal API contract when work crosses a boundary, what's in and out of scope, and what to report. Describe the problem, not your preferred answer — for `designer` especially, a suggested solution is labelled as one hypothesis to test against alternatives, since a designer handed a placement tends to confirm it. Every agent ends with the same report shape (changed, verified, deviations, needs the user), so you don't need to restate it.

**Visible choices go to the user.** Technical and internal calls (an order of operations, a timeout, which error code a failure reuses) can be made on the user's behalf and recorded in an ADR or issue. A *visible choice* goes to the user as a question, with a recommended answer, before it's built: one that changes what a screen shows or says, or where something lives, **beyond** what the brief, an approved artboard or ADR, or an existing token or pattern already settles. Values chosen within an approved direction (spacing, a token, copy polish) are not questions. Why: an agent or doc marking a visible choice "settled" is how it ships without the user ever seeing it.

**Reports to the user end with "Decided for you"**: the calls made on the user's behalf since the last report, one line each, with where each is recorded and what reversing it would take; omit it when there were none. This is the orchestrator's report to the user, not a fifth section for agents. Why: the user can catch and reverse a call without reading every ADR.

**Shell access.** An agent's shell has worked in some sessions and not others. Don't assume either way; whatever they report, re-run the checks yourself.

**Tiers follow the cost of being wrong.** Each agent file names a `tier`, not a model (`tests/agents.test.mjs` in the agent-config repo checks it), and the build maps the tier to each tool's model dialect (`docs/architecture.md`, Agents). `judgment` where the call is hard to reverse and only a person checks it: scope, boundaries, placement, a threat model, a review. `implementation` where the output is cheap to redo and is checked before it lands, by lint and tests, by you re-running every check, or by the PR diff being read: implementation, tests, config, docs. The session keeps the strongest model: orchestration and the review passes are where whole-conversation judgment pays, and an agent sees only its brief. A fan-out search uses a read-only search agent on the cheapest model the tool offers (Claude Code: `Explore` with `model: haiku`); a cold-start check runs at least at the implementation tier, because a model that finds little is the failure that check exists to catch. Move one dispatch up a tier for a stated reason (a change that alters a contract across a service boundary) or down (a one-line config fix) with the dispatch's model override where the tool has one, never by editing the file for one task.

### New product idea

1. **product-strategist** scopes it. 2. **architect-engineer** makes the first phase's technical calls. 3. **designer** designs the key flows. 4. Then the feature pipeline below.

### Feature pipeline

Small, single-file changes skip this. For anything larger, follow this order, skip stages that don't apply, and keep a todo list with one item per stage so nothing gets dropped between handoffs.

1. **architect-engineer** — only when the change spans features/layers or introduces a new pattern.
2. **designer** — whenever the change renders on more than one route or touches global chrome (header, nav, switchers, layout shells), adds or changes a primitive, token or variant, introduces a UX pattern the repo doesn't have, or needs a *home* (a new section, page or entry point) even if its parts exist. The test is how many routes and states it touches, not the size of the diff. The designer hands back a spec — placement, states, exact values, behaviour at 390/768/1280 — that implementation doesn't re-decide, plus an HTML artboard for a new or changed screen. Publish the artboard and get the user's approval before dispatching implementation.
3. **backend-engineer** and the client's engineer (**frontend-engineer**, **android-engineer**, **ios-engineer** or **react-native-engineer**) implement. If a feature spans both, write the API contract first and hand the literal contract to each.
4. **qa-engineer** verifies — for UI, including the mobile Playwright project (web, Flutter) or the phone-and-tablet runs (native Android, iOS, React Native), and the screenshots the Testing rules ask for.
5. **security-engineer** — auth, payments, external input, data exposure.
6. **technical-writer** — when user- or developer-facing docs change.
7. **devops-engineer** — when Docker, CI/CD or Cloudflare config changes.
8. A review pass before calling it finished; for UI, also the `web-design-guidelines` skill (contrast, target size, semantics). Review the PR's worktree when one exists, by its absolute path (on Claude Code `/code-review <level> <absolute worktree path>`, the form that has worked: the reviewer runs inside that directory and diffs against a fetched `origin/main`); a PR URL makes the reviewer fetch it somewhere, and that somewhere has been a served checkout. **Every review brief includes architecture** alongside correctness and security: paste the stack skill's "Checklist for a review brief" into it, plus layering, `shared/` vs feature placement, interface width, file and function size, comment history (the structure rules above). A new violation is a request for changes, not a nit.
9. `retro` when something slipped: a review or CI caught what an earlier stage should have, the user corrected the approach, a gate was skipped, or an agent's claim didn't hold. It files fixes to the setup as issues for the user to approve, never edits them in directly.

## Workflow

- **Trunk-based with a PR gate.** Short-lived branches off the default branch, merged within a day or two through a reviewed PR; no direct commits to trunk. Work that can't ship complete in that window lands behind a feature flag. The `git-guard` hook (`.agents/hooks/git-guard/git-guard.mjs` in the agent-config repo; its header comment lists what it refuses, and its tests pin the forms) blocks the git and gh commands that bypass this workflow or disturb a served checkout; a block is an instruction to do what its message says, never something to work around.
- Create PRs with the `open-pr` skill, which runs the merge gate's review loop before the PR exists (a PR opens reviewed; opening first and reviewing after is how an unreviewed PR gets merged); work through review with `resolve-pr-comments`, write commits with `conventional-commit`, inspect PRs with `gh`.
- **Fast on every PR, full on release.** GitHub Actions minutes are budgeted (3,000 a month across every repo), so each repo's CI has two tiers. Every PR push and every push to trunk runs the fast tier: lint, typecheck, unit and fast integration tests, build, and for a web app the Playwright smoke set, a few minutes in all. The full Playwright suite runs on a `v*` tag, on a weekly schedule against trunk, and on a manual run; where there is a full tier, a red scheduled or release-tag run opens an issue, because no PR is there to turn red (whoever pushes a tag watches its run; the weekly run is the unattended one). A newer push cancels the older run on a PR, never on trunk or a tag; a change to docs or feature readmes alone runs nothing; every job has a `timeout-minutes`. PRs open ready for review, not as drafts. **Before pushing, run the e2e specs the change touches locally**: on a PR, CI no longer does. `templates/ci.yml` in the agent-config repo is the starting point for a new repo; each repo's `.github/workflows/ci.yml` is the source of truth for what runs when.
- **Every Node repo has a committed pre-push hook** (`.githooks/pre-push`, installed by its `prepare` script on `npm ci`) that mirrors the fast tier's cheap checks: lint, typecheck, unit tests, and the contract check where the repo vendors one; no build, no Playwright. `templates/pre-push` and `templates/install-git-hooks.mjs` (a shim in the repo's shared hooks directory, never `core.hooksPath`) are the starting point. Why: CI minutes are budgeted and most red runs were checks a local run catches.
- **Releases are tags.** Tag trunk `vX.Y.Z`, plain and per repo; that tag's full run is the release gate.
- **A whole-repo security audit before a release that touches auth, payments or external input**, and after a security-sensitive milestone: the `security-audit` skill, run from the main session (it dispatches its own hunters and verifiers, which an agent can't). Confirmed findings become issues; `needs_validation` ones go to the user. Per-change review stays with `security-engineer`.
- **Merging is the user's call** unless they grant it. Where they do, merge only after all three, then squash-merge and delete the branch:
  1. The review loop has converged: every correctness bug a high review pass found is fixed, and a medium pass then reports no verified correctness bugs on the main paths (high passes always find nitpicks, so they never converge on their own).
  2. The PR's CI (the fast tier) has finished green on its last push, if the repo has CI and the push triggered a run. No run counts as green only when every changed file is one the workflow's `paths` filter excludes; a workflow file that fails to parse also produces no run, and that is red; a pending run means keep waiting, because a wait that times out is never a reason to merge.
  3. You've re-run the checks yourself, the e2e specs the change touches included. Where the repo vendors another service's contract, fetch the producer clone (`git -C <producer clone> fetch`), then re-run `contracts:check` right before merging: main may have moved since the last push, and drift on main blocks deploys. Order of producer and consumer changes: "Contracts aren't refactors".
- **The review loop is bounded.** A main path is one a documented user flow, a smoke spec or a published contract exercises; in a repo with none of those (the agent-config repo, a hook, a library) it is the behaviour the tests and the PR description claim; everything else is a rare path. Treat a finding as unverified unless it carries a `CONFIRMED` verdict, and verify it before acting on it. A verified bug on a main path is fixed in the PR. A new edge case on a rare path, or a finding that only re-litigates a judgment call an earlier pass settled, goes to a tracked follow-up issue instead of another round. After two medium rounds that still find new main-path bugs, stop and bring the user the remaining list with a recommendation: merge behind a flag, simplify, or keep going.
- **Use a git worktree when the main checkout is serving a running dev server.** Worktrees share the repo's hooks but not untracked files (`.env`, `.env.local`, `node_modules`), so copy or install what's needed. Remove the worktree once its PR is merged, never one with unpushed work; the review and the merge-gate checks run in it. A new branch's worktree is `git fetch`, then `git worktree add ../worktrees/<repo>-wt-<name> --no-track -b <type>/<name> origin/main` run in the repo (the hook's block message gives the same command, and `.agents/hooks/git-guard/git-guard.test.mjs` keeps the two equal), then copy the env files and `npm ci`. Every worktree lives in one `worktrees/` folder beside the clones (git creates it), so the folder that holds the clones stays readable. Push it with `git push -u origin <branch>`. A reviewer diffs the branch against a fetched `origin/main`, never against the branch's own upstream or a local `main`, which may be stale. If the worktree is gone when review fixes come, `git fetch && git worktree prune`, then `git worktree add ../worktrees/<repo>-wt-<name> -B <branch> origin/<branch>`, which resets the local branch to the remote. When an agent works in a repo other than the session's own, create its worktree yourself that way and give the agent the absolute path; a tool's built-in worktree isolation (Claude Code's Agent `isolation: worktree`) isolates the session's repo, not the target's. Checkouts that serve a dev server are listed in `~/.config/agent-config/git-guard.json`, and the hook refuses to switch branches, or to stash or apply a stash, in them.
- **Push without asking in a project whose standards grant the agent merge rights**; a project that lets you merge has already let you push. The agent-config repo itself (`juanagu/agent-config`) grants push and, under the gate above, merge; it has no CI, so `npm test` run locally, the hook suite included, is its whole automated gate. Elsewhere, confirm once per branch.
- Secrets never in git: `.env` ignored, `.env.example` committed with keys and no values.
- Backend logging is structured, never `console.log`, never secrets or PII.

## Task tracking

- GitHub Issues plus a Project board (Todo / In Progress / Done), seeded from the plan doc with one issue per feature.
- **Seed thin, enrich just in time.** A seeded ticket is a title and a link. Right before dispatching it, write the real detail into the issue itself — context links, scope in/out, API contract if it crosses a service boundary, acceptance criteria, dependencies — and draw the dispatch prompt from it, so the spec outlives the chat.
- **Retrofit when the PR lands**: what was actually built, the real contract, what was deferred, criteria ticked.

## Knowledge

**The repo is the memory; the conversation is a cache.** A transcript gets compacted and ends, and knowledge that exists only there is knowledge the project doesn't have.

- Anything decided on the user's behalf lands in an ADR or the issue before the session ends, never only in chat.
- Each kind of knowledge has one home: scope in the plan doc; system shape in the architecture doc; a decision with its alternatives in an ADR; what a feature is for the user, across repos, in its `docs/features/` doc; what a feature's code exposes in its `feature_readme.md`; how to run it, and what bites, in a development doc; status on the board. None of them mirrors another.
- The tool's local memory holds only machine and toolchain facts and the user's working preferences. Project knowledge goes in the repo, with at most a pointer in memory.
- A project's `AGENTS.md` stays short, because it loads every session, and points at those docs instead of restating them. A `CLAUDE.md` that imports it (`@AGENTS.md`) lets Claude Code read the same instructions where it cannot read `AGENTS.md` directly.
- **Cold-start check after each milestone.** Dispatch a fresh read-only agent with no history (Claude Code's `Plan` agent), only the working directory and the next ticket. Ask it for an orientation, the run recipe as the docs give it, a plan, and a gap report where each gap names what it looked for and where. Say plainly that you want gaps found, not reassurance: left to itself it reports politely and finds little. Fix the gaps that would really stall someone; drop the ones that would only lengthen the docs.

## Feature flags

- Named `feature.<area>.<name>`, read through one central flags module per project, checked at the feature's entry point (route, top-level component) rather than deep in business logic.
- Default off in production. Remove the flag and its dead path once fully rolled out; note the planned cleanup point when introducing it.

## CodeGraph

In a repo with a `.codegraph/` directory, use it before grep/find or reading files to locate or understand code: the `codegraph_explore` MCP tool where the tool supports MCP (load it via tool search if deferred), or `codegraph explore "<symbols or question>"` in the shell. With no `.codegraph/`, skip it — indexing is the user's decision.
